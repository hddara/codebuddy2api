# App 设计规范

> **规范的来源**：对 TinyPick（一个「帮助用户理性做决策」的 App）全部 10 张真实界面截图的反向解析。
> 素材归档：`HDdaraAi/docs/design-ref/tinypick/p1.png ~ p10.png`
>
> **本文档的定位**：**方法论层**。它回答「一个 App 凭什么看起来专业」「特色从哪来」，
> 而**不下发具体色值、圆角、字号**——那些是规范的**产物**，不是规范本身。
> 具体数值由各项目的令牌层（Design Tokens）承载，见 §7。

---

## 0. 一句话结论

TinyPick 好看不是因为配色好看，而是因为**它把一件事想透了，然后让每一层都服从那件事**。

它的产品内核是**「一条闭环流程」**（分析 → 决定 → 执行 → 复盘）。
于是：视觉层用它当锚点，色彩层用它定语义，信息架构直接用它的分段，
连空状态和提示语都在复述它。

**这就是「特色」的来源——不是装饰，是内核在每一层的投影。**

---

## 1. 第一性原则：特色 = 内核的可视化投影

大多数「没特色」的 App 都犯了同一个错：**内核是抽象的，界面是通用的**。
于是界面只能靠「加渐变、加图标、加动效」来假装有特色——这就是"贴皮肤"。

TinyPick 的做法相反：

| 它的内核 | 界面上的投影 |
|---|---|
| 四阶段闭环 | 首页第一屏就是**四节点流程条**（黑卡 + 彩圈 + 连线），是视觉锚点 |
| 每个决策有状态 | 四个状态各有专属色，**贯穿胶囊、图标、按钮、流程节点** |
| 决策要能回溯 | 详情页按「决定信息 / 执行决定 / 结果复盘」**三段分组**，直接复述流程 |
| 结果要能对比 | 支持/反对**双栏对撞**（绿卡 vs 红卡），分值正负用色区分 |
| 建议只是参考 | 提示语原文照写进界面：「TinyPick 的建议仅供参考。你可以做出不同的最终选择。」 |

**规范条目 1.1**：先写出产品的**一句话内核**（做什么、为谁、凭什么）。
**规范条目 1.2**：找出内核里**最独特的那个结构**（流程？层级？对比？时间线？），把它做成界面的视觉锚点，出现在用户第一眼看到的位置。
**规范条目 1.3**：禁止在没有内核投影的前提下加装饰。**任何视觉元素都要能回答「它对应产品的哪一点」。**

## 2. 视觉语言层

### 2.1 层级（Hierarchy）：用「面」不用「线」

TinyPick 全程**几乎不用边框和阴影**。它靠三件事区分层级：

1. **背景色差**：页面底是极浅冷灰（近白但不纯白），卡片是**纯白**。靠 4~6% 的明度差把卡片"浮"起来。
2. **圆角容器**：所有内容都装在圆角矩形里，**没有裸内容直接铺在页面上**。
3. **留白尺度**：卡片之间、卡片内部分区的间距是**统一的节奏**。

**规范条目 2.1.1**：层级优先用**背景明度差**表达，其次用**留白**，最后才考虑边框/阴影。
**规范条目 2.1.2**：页面底色与卡片底色必须有可辨差异（建议 4%~8% 明度差），且**全 App 只用这一对**。
**规范条目 2.1.3**：禁止给卡片加"深阴影"来强调层级——那是 Web 老派做法，移动端会显脏。
**规范条目 2.1.4**：**内容一律装箱**。裸文字/裸列表直接铺页面 = 未完成的设计。

### 2.2 层级（文字）：三层灰阶，绝不混用

TinyPick 的文字只有**三层语义**：

| 层级 | 用途 | 表现 |
|---|---|---|
| 主 | 标题、金额、关键数字、选项名 | 近黑、加粗、字号最大 |
| 次 | 说明、时间、meta 信息 | 中灰、常规字重 |
| 辅 | 分组标签、提示、脚注 | 浅灰、更小字号 |

**规范条目 2.2.1**：**文字灰度只有三级**，不允许出现第四、第五种灰度。
**规范条目 2.2.2**：**字号级差要能被一眼看出**。相邻两级至少差 2rpx 且**字重必须不同**——只靠 1rpx 差异区分等于没区分（这是最常见的设计缺陷）。
**规范条目 2.2.3**：**分组标题放在卡片外、用「辅」级**；卡片内的字段标签用「次」级。二者不可互换。

### 2.3 色彩：语义色是系统，不是调色板

TinyPick 的色彩体系值得逐条记下：

- **品牌色只有两个**：橙（品牌标题）+ 绿（Logo、进度、推荐、主按钮）。
- **状态色有四组**，每组对应流程的一个阶段：分析中=绿 / 待执行=蓝 / 待复盘=橙 / 已复盘=青。
- **语义色两组**：正=绿、负=红（支持/反对理由、分值正负）。
- **中性色一套**：页面底、卡片白、三级文字灰。

关键：**同一个语义在任何地方都是同一个色**。
「待复盘」的橙，同时出现在：状态胶囊的底色、流程节点的圆环、「立即复盘」按钮的填充、进度条。
**用户不需要看图例就能建立映射。**

**规范条目 2.3.1**：颜色分四类管理——**品牌色 / 状态色 / 语义色 / 中性色**。每类都必须有明确定义，且**总量要克制**（品牌色 1~2 个、状态色按状态数、语义色 2~3 组）。
**规范条目 2.3.2**：**同一语义全 App 同色**。禁止"A 页面用蓝表示进行中，B 页面用橙"。
**规范条目 2.3.3**：品牌色**不是主按钮色**。主按钮用品牌色或语义主色皆可，但**一个界面只能有一个"最强调"的按钮**（见 §3.2）。
**规范条目 2.3.4**：禁止在业务界面使用**渐变**，除非它是品牌标识的一部分（Logo、启动图）。
**规范条目 2.3.5**：状态色必须有**配套的浅底版本**（用于胶囊背景），与文字色形成对比，保证可读。

### 2.4 形状：一套圆角，按角色分级

TinyPick 的圆角是**分角色**的，不是随意值：

| 角色 | 相对尺度 | 例子 |
|---|---|---|
| 大容器 | 最圆 | 卡片、面板、流程黑卡 |
| 控件 | 中等 | 按钮、输入框、胶囊按钮 |
| 全圆 | 100% | 状态胶囊、标签、头像 |

**规范条目 2.4.1**：圆角**按角色**定义（容器 / 控件 / 全圆），**不允许同一角色出现两种值**。
**规范条目 2.4.2**：圆角尺度要与元素尺寸**成比例**——小元素用大圆角会显笨，大容器用小圆角会显硬。
**规范条目 2.4.3**：圆角必须**严格一致**。`20rpx` 与 `24rpx` 的差别人眼能看出，且会让人觉得"没做完"（这是 HDdaraAI 现有最明显的问题之一）。

### 2.5 间距：用节奏，不用感觉

**规范条目 2.5.1**：间距只有**三档语义**——页面级（外边距）、区块级（卡片间）、行内级（元素间）。三档之间保持**稳定的倍数关系**。
**规范条目 2.5.2**：**同一类元素在任何页面的间距必须相同**。同一个「卡片到卡片」的距离，全 App 只能有一个值。
**规范条目 2.5.3**：留白要**宁多勿少**。移动端拥挤的解药永远是删内容，不是缩间距。

## 3. 交互层

### 3.1 主次分明：一个界面只有一个主角

TinyPick 的详情页有**两个按钮**，但绝不混淆：
- 「执行该决定」= 品牌色 / 语义主色 **实心填充** = 主操作
- 「重新做决定」= **描边 + 无填充** = 次操作

且**主按钮在右**（符合拇指热区与从左到右的阅读终点）。

**规范条目 3.1.1**：每个界面/视区**只能有一个视觉最强调的元素**（主按钮或主数据）。
**规范条目 3.1.2**：按钮**三级制**——实心（主）/ 描边或灰底（次）/ 纯文字（第三级）。**不允许两个实心按钮并排**。
**规范条目 3.1.3**：破坏性操作（删除、清空）**必须用语义危险色**，且需要二次确认。

### 3.2 状态可见：让用户永远知道「现在在哪」

TinyPick 的流程条把「当前处于哪个阶段」常驻在首页第一屏，且各状态在列表里用胶囊重复标注。

**规范条目 3.2.1**：**任何异步数据区都必须有完整四态**：加载 / 空 / 错误 / 有数据。缺一个就是未完成。
**规范条目 3.2.2**：列表首屏加载**优先用骨架屏**（保留布局轮廓），不用整屏转圈——转圈会让页面"闪一下"。
**规范条目 3.2.3**：状态**必须可辨识**（颜色 + 文字双通道），不能只靠颜色（色盲可用性）。
**规范条目 3.2.4**：错误态**必须给出下一步动作**（重试 / 换个地址 / 检查网络），不能只报"失败了"。

### 3.3 就地处理：能内联就不跳页

TinyPick 的分段控件切换后，**表单内容在同一屏内替换**（支持反对 ↔ 加权矩阵），不跳新页面。

**规范条目 3.3.1**：可逆的、轻量的选择**优先内联**（分段控件、折叠、展开），避免页面跳转与回退。
**规范条目 3.3.2**：**危险或不可逆**的操作才用独立页面/弹窗，并要求确认。
**规范条目 3.3.3**：表单**就地校验、就地报错**，错误信息紧贴出错的字段。

### 3.4 输入即反馈：实时展示计算结果

TinyPick 在新增理由页的标题栏**实时显示汇总**（`买房 6 : -2.5`，正负用色区分）。
用户每加一条理由，都能立刻看到总分的移动。

**规范条目 3.4.1**：表单中任何影响结果的输入，**必须就近实时回显结果**（总分、字数、预估、剩余量）。
**规范条目 3.4.2**：实时反馈的**数值变化要有视觉强调**（颜色/字重），让变化被看见。
**规范条目 3.4.3**：涉及"不可逆或代价高"的输入，**在控件上方给解释性提示**（TinyPick 原文："TinyPick 的建议仅供参考。你可以做出不同的最终选择。"）。

### 3.5 手势与点击：移动端的基本礼仪

**规范条目 3.5.1**：**点击目标最小尺寸**必须满足触控标准（≥ 44×44 逻辑像素）。文字按钮要加隐形热区。
**规范条目 3.5.2**：**任何可点元素必须有点击反馈**（背景变化 / 透明度 / 缩放），且反馈**立即**（无延迟感）。
**规范条目 3.5.3**：列表项**支持滑动操作时，必须有可见提示**（TinyPick："左滑可删除决策事项"）。
**规范条目 3.5.4**：`@tap` 之类的响应式事件**必须用语义化可点元素**（`<button>` 等），否则在部分运行时无响应——这是真机实测的硬约束，不是偏好。

## 4. 内容层（文案也是设计）

TinyPick 的文案有三个特点，都可直接学：

1. **直说价值**："它给的建议只是参考。对我来说，更有用的是看清自己当时怎么想，以及后来发生了什么。"
2. **承认边界**："TinyPick 的建议仅供参考。"
3. **引导而非命令**："你可以添加备注哦"（而不是"请添加备注"）

**规范条目 4.1**：**禁止机械文案**。不说"操作成功"「数据加载失败」，要说**具体发生了什么 + 下一步做什么**。
**规范条目 4.2**：**空状态要有价值**。空列表不是终点，应说明"这里会有什么"+"怎么产生第一条"。
**规范条目 4.3**：**提示语放在需要它的位置**，不堆在页面顶部。
**规范条目 4.4**：**术语全 App 统一**（同一个东西只能有一个叫法）。
**规范条目 4.5**：**产品名/品牌名的写法必须唯一**。大小写混用（`HDdaraAI` vs `HDdaraAi`）会直接损害专业感。

## 5. 一致性层（体系的生命线）

TinyPick 从封面到第 10 张截图，**没有一个页面脱离体系**。
卡片圆角、按钮样式、分段控件、步进器、状态胶囊——**跨页面完全相同**。

**规范条目 5.1**：**同一类元素跨页面必须像素级一致**。若发现两处不一致，必须收敛到同一处定义，而不是各改各的。
**规范条目 5.2**：**禁止页面内硬编码样式值**。所有颜色、圆角、间距、字号**必须来自令牌层**。
**规范条目 5.3**：**重复出现 3 次的 UI 必须组件化**。同一段样式写第三遍时，就是抽取组件的信号。
**规范条目 5.4**：**新增页面必须复用既有组件**，不允许"另起一套"。
**规范条目 5.5**：**允许有意的例外，但例外必须有理由并写进文档**——不允许"无意的例外"（那叫不一致）。

## 6. 反模式清单（不合格的 App 长什么样）

以下每条都在真实项目中反复出现，逐条对照自检：

| # | 反模式 | 为什么不合格 |
|---|---|---|
| 1 | 每个页面各写一套 `.card` / `.primary` | 一致性全靠人肉维护，必然漂移 |
| 2 | 圆角 20rpx / 24rpx / 18rpx 混用 | 人眼可辨，显"没做完" |
| 3 | 颜色字面量散落各处 | 改主题要全文搜索，必然漏改 |
| 4 | 文字只有"黑"和"灰"两种 | 信息层级无法建立 |
| 5 | 没有空状态 / 用"暂无数据"糊过去 | 用户不知道发生了什么、该做什么 |
| 6 | 整屏 spinner 代替骨架屏 | 布局跳动，显廉价 |
| 7 | 两个实心主按钮并排 | 主次不分，用户要读文字才知道点哪个 |
| 8 | 业务界面用渐变装饰 | 廉价感的最大来源 |
| 9 | 图标用文字符号凑（`›`、`+`） | 线条粗细/基线对不齐，观感粗糙 |
| 10 | 品牌名大小写不统一 | 最伤专业感的低级错误 |
| 11 | 产品名/术语在不同页面叫法不同 | 增加认知成本 |
| 12 | 只做浅色主题不规划暗色 | 后期改造成本极高（**可以不做，但要有意为之**） |

## 7. 落地结构：规范在工程里怎么承载

规范若不落到代码结构里，就是一张废纸。**四层结构**：

```
① 令牌层  (Design Tokens)
   颜色 / 圆角 / 间距 / 字号 / 字重的唯一定义处
   ↓ 被引用
② 基础组件层  (Primitives)
   Button / Card / NavBar / Tag / Skeleton / Empty / Field / Segmented
   每个组件内部只消费令牌，不写字面量
   ↓ 被组合
③ 业务组件层  (Composites)
   DecisionCard / FlowBar / ScoreRow  ← 内核投影的载体
   ↓ 组装
④ 页面层  (Pages)
   页面只做布局与数据，不定义视觉
```

**规范条目 7.1**：**页面层不允许出现颜色/圆角字面量**——出现即视为缺陷。
**规范条目 7.2**：**基础组件必须覆盖四态**（默认/按下/禁用/加载）。
**规范条目 7.3**：令牌的命名要**按语义**（`text-secondary`、`surface`、`danger`），**不按外观**（`gray-500`、`red`）——按外观命名会让"换色"变成"改名"。
**规范条目 7.4**：**令牌只有一份**。若某个工具（如 CSS 框架配置）需要镜像，必须由**构建期自动生成**，禁止手工维护两份。

## 8. 交付前的自检清单

一个界面「做完」之前，逐条过：

**内核**
- [ ] 这个界面能回答「它对应我产品的哪一点」吗？
- [ ] 视觉锚点是否出现在用户第一眼能看到的位置？

**层级**
- [ ] 卡片与页面底有可辨色差吗？内容都装箱了吗？
- [ ] 文字只用了三级灰阶吗？相邻级别能一眼分辨吗？

**色彩**
- [ ] 同一个语义在全 App 是同一个色吗？
- [ ] 有没有出现渐变装饰？有没有第四个品牌色？

**形状与间距**
- [ ] 同类元素（卡片/按钮/输入框）的圆角全 App 一致吗？
- [ ] 同类间距全 App 一致吗？

**状态**
- [ ] 加载/空/错误/有数据四态齐全吗？
- [ ] 加载用的是骨架屏还是转圈？
- [ ] 错误态有没有给出下一步动作？

**交互**
- [ ] 这个界面只有一个最强调元素吗？
- [ ] 点击目标 ≥44px 吗？点击有立即反馈吗？
- [ ] 表单有实时反馈吗？

**一致性**
- [ ] 有没有硬编码颜色/圆角/间距？
- [ ] 有没有第三处重复的样式该抽组件？
- [ ] 品牌名/术语写法统一吗？
