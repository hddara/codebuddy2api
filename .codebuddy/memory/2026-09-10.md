关键设计决策：

1. **调度载体**：不用外部 cron，复用 `instrumentation.ts`（项目已有 `refreshMissingCredentialModels()` 先例），定时器挂 `globalThis` 防热重载重复注册，`setTimeout(...).unref()` 不阻塞进程退出。
2. **时间语义**：按进程本地时区（= 容器 `TZ`）解释 `HH:mm`，与 cron 习惯一致；不额外引入时区配置项，改由文档说明用 `TZ`。
3. **按日去重 + 有界重试**：持久化 `checkin/state`。第一次实现只按「日期是否已跑过」去重，review 时发现缺陷——上游整体不可用时 `checkinAccount` 内部 catch 成快照错误而不抛异常，会导致当天被误标完成、整天不再签到。改为：只要有一个账号成功（或当天无可用账号）才算完成，否则 1 分钟后重试，上限 3 次/天（防止坏账号变成无限循环）。传输层抛异常同样计一次尝试并记录错误。
4. **观测**：结果打日志 + `/health` 暴露 `enabled` / `next_run_at`；**没有**改动 `/admin-api/account-status` 的响应结构，因为 e2e 里对该接口用了 `toEqual({credentials:[],statuses:[]})` 严格断言。

- 教训（已写入 MEMORY.md）：新增自定义 storage namespace 必须同步改 `getDocumentPath()`；只 mock storage 的单测测不出这个类别的缺陷。

## 追加：研究「怎么启动服务」（只用现有 node/npm，不新增工具）

### 实测结论

1. **不需要 bun**：`node_modules/.bin/next` 的 shebang 是 `#!/usr/bin/env node`；node v24.0.2 + npm 11.3.0 足够。
2. **开发**（实测 /health 200，Ready in 371ms）：
   `CODEBUDDY_SAFE_DELETE_ENABLED=0 node node_modules/next/dist/bin/next dev --hostname 127.0.0.1 --port 3010`
   注意 **3000 端口被 grafana 占用**，必须显式指定端口；docs 里的 `bun run dev`(3000) 在本机起不来。
3. **构建**：`CODEBUDDY_SAFE_DELETE_ENABLED=0 npm run build` 成功，产出 `.next/BUILD_ID` + `.next/standalone/server.js`。
4. **生产（=Docker 形态，实测 /health、/login、/dashboard、静态 chunk 全 200）**：
   `cp -R .next/static .next/standalone/.next/static` → `cp -R public/. .next/standalone/public/` → `cd .next/standalone && NODE_ENV=production HOSTNAME=127.0.0.1 PORT=3012 node server.js`
5. **`next start` 不是本项目的生产入口**：Next 16 明确警告 `"next start" does not work with "output: standalone" configuration. Use "node .next/standalone/server.js" instead.` Docker 的 `CMD ["bun","server.js"]` 里 bun 只是基础镜像选择，同一文件用 node 也能跑（已实测）。
6. `output: "standalone"` **不会**自动把 `.next/static` 与 `public` 放进 standalone 目录，必须自己拷（Dockerfile 用 COPY，本地用 cp），否则页面是 HTML 但静态资源 404。

### 重要：IDE safe-delete shim 会让 next build 挂死

- 现象：不带 `CODEBUDDY_SAFE_DELETE_ENABLED=0` 时 `npm run build` 卡在 `✓ Running next.config.ts` 后无输出。
- 根因：build 开头清理 `.next`（远超 shim 的 500 文件阈值）→ shim 抛 SAFE_DELETE_BULK_CONFIRM_REQUIRED 后**阻塞等确认**。
- 连带：卡住的 build 一直占着 `<distDir>/lock`（Next 用 native flock，见 `node_modules/next/dist/build/lockfile.js`，路径 `.next/lock`），导致下一次 build 报 `Another next build process is already running.`
- 排障：`ps ax -o pid=,command= | grep "dist/bin/next"` 找到并 kill；**不用手工删 `.next/lock`**（flock 随进程退出释放）。
- 这也为之前"Playwright --ui 卡在 Loading…"提供了更具体的机制：build 清理 `.next`（含 dev 依赖的 `.next/dev`）把运行中的 dev server 打坏，而 `reuseExistingServer: false` 让 Playwright 死等 webServer。仍属强相关、非严格证明。

### 拆分前必须先解决的两个交叉依赖（这是关键发现）

1. **跨 tab 派发 effect**（约 1474-1510 行）：一个 effect 用 `if (activeTab === ...)` 串起了全部 6 个 tab 的首次加载，并在 cleanup 里统一 `clearAuthTimer() / clearDebugAutoRefreshTimer() / clearUsageTimer()`。
2. **`refreshAdminData`**（761-764 行）：会同时刷新 dashboard + credentials + models，但**只被凭证类操作调用**（保存凭证 / 新增凭证 / 删除凭证），不是全局刷新。

### 定下的设计

既然**只有当前 tab 的 controller 会被挂载**，就让每个 controller 自己负责自己的加载与清理，直接删掉那个派发 effect：

```tsx
// app/debug/debug-controller.tsx（示例：debug）
export const DebugTabController = ({ children, initialData }) => {
  const [debug, setDebug] = useAtom(debugStateAtom);
  useHydrateAtoms(...)            // 自己水合自己的 atom
  // loadDebug / loadDebugDetail / saveDebugSettings / saveDebugEnabled / clearDebugItems 原样迁入
  useEffect(() => { if (!initialData) void loadDebug(); }, [initialData]);   // 替代派发 effect
  useEffect(() => { ...自动刷新定时器...; return clearDebugAutoRefreshTimer; }, [...]);
  return <DebugProvider value={{ ... }}>{children}</DebugProvider>;
};
```

- 语义等价性：原 effect 在 `activeTab` 变化时会清掉三个定时器；拆开后切走 tab 会卸载对应 controller 从而触发它的 cleanup，效果一致。
- `refreshAdminData` 整体归入 **credentials controller**（只有它用），它跨 tab 刷新 dashboard 的行为保持不变。
- `page-shell` 最终只保留：布局骨架（`.console-workspace` / `.console-main` / `.console-header` 透传）+ 导航 + 各 tab controller 的条件挂载。

### 执行顺序（每个 tab 一次，迁完立刻验证）

dashboard（最小，先验证模式）→ debug → settings → api-test → usage → credentials（最大，含 refreshAdminData）

### 补充：跨 tab 失效的最后一环（易被忽略）

`refreshAdminData` 不只是「刷新 credentials」，它同时刷新 **dashboard**（`Promise.all([loadDashboard(), loadCredentials()])` + `loadCredentialModels()`），是典型的**跨 tab 失效**。
所以不能把它整体归入 credentials controller —— dashboard 的 `loadDashboard` 一旦搬进 dashboard controller，credentials 侧就够不着了。

解法：**jotai 失效信号 atom**。owner 侧监听信号重载，触发侧只 bump 计数，双方互不引用：

```ts
export const dashboardRefreshSignalAtom = atom(0);
// dashboard-controller:
useEffect(() => {
  if (!initialData || signal > 0) void loadDashboard();
}, [signal, initialData]);
// credentials-controller（凭证增删改后）:
const bumpDashboard = useSetAtom(dashboardRefreshSignalAtom);
bumpDashboard((n) => n + 1);
```

结论：拆分设计至此闭环，可以开始按 dashboard → debug → settings → api-test → usage → credentials 顺序执行。

### 关键设计细节：信号必须是一次性的

第一版写成 `if (!hasInitialData || refreshSignal > 0) loadDashboard()`，**有隐患**：信号只增不减，用户只要改过一次凭证，此后每次进 dashboard 都会重复请求。

useEffect(() => {
  if (!hasInitialData) void loadDashboard();

  setRefreshSignal(0); // 消费掉，避免后续 mount 重复请求

}, [loadDashboard, refreshSignal, setRefreshSignal]);
