### 1. 会话管理 + 会话数据持久化 → 未实现

必须先区分两个"会话"：

| 含义                                    | 状态                                 | 证据                                                                                                                                                                                                                     |
| --------------------------------------- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **登录会话**（管理员 cookie/token）     | **已完整实现**                       | `lib/server/admin/session.ts`：namespace `admin-auth`/`state`；cookie `codebuddy_admin_session`、TTL 8h；只存 `sha256(token)`；`getValidSessionRecord` 校验并刷 `lastUsedAt`；路由 `app/admin-api/auth/session/route.ts` |
| **对话会话**（请求方 ↔ 上游的对话内容） | **基本未实现**，只有一个内部短期缓存 | 见下                                                                                                                                                                                                                     |

对话侧唯一的存在物是 **Responses API 链路的 response session**：

- `lib/server/proxy/responses.ts:138-139`：namespace `responses` + `response-session-index`
- 含 `accessKeyId` 与 `transcript`（:64-73、90-102）
- 用途**仅**为 `previous_response_id` 拼接上下文（:958-1017）
- 限额：TTL 1 小时、单条 8MB、总量 64MB、最多 1000 条（:133-137）→ 是短期缓存，不是对话归档
- **非 Pg 后端只存内存 Map**（`globalResponsesState`，:145-173），重启即丢
- **没有**任何 admin-api 路由可列出/查询/删除会话；**没有**前端页面

其余链路（chat/completions、anthropic、codebuddy）**完全不持久化对话内容**。

`lib/server/domain/account-status.ts` 里的 "account" 是**上游 CodeBuddy 账号的额度/签到**，与会话无关，别混淆。

### 2. 账户管理 + 不同账户不同权限 → 未实现

- 系统实质只有**单一管理员账号**：管理员密码（scrypt）+ WebAuthn passkey + 会话 cookie
- `AdminAuthState` 只有单数 `password` + 单个 `username`，**没有 `users[]`/`accounts[]`**（`lib/server/admin/session.ts:77-84`、`ADMIN_USER_ID = 'codebuddy-admin'` :31）
- 存储层实际使用的 namespace 只有：`config`、`admin-auth`、`access-keys`、`debug`、`credentials`、`usage`、`responses`、`response-session-index` —— **没有 users/accounts/roles/permissions**
- DB schema 只有三张业务表：`documents`（通用 namespace/key）、`usage_events`、`debug_logs` —— **没有用户表**
- `AdminRole`/`AdminProfile`（`app/page-data.ts:19-27`）是**我为阶段 2 预留的类型**，`role` 在 `app/page.tsx:62` 硬编码为 `'owner'`，**从未参与任何权限判断**；前端只在 `app/user-menu.tsx` 把它映射成显示文案

### 两个实现细节坑

1. `StoredPasswordRecord` **必须带 `updatedAt`**，且类型是 **ISO 字符串**（不是 number）。第一版只传 `{hash, salt}` → tsc 报缺字段；补成 number 又报 `number is not assignable to string`。正确写法：`updatedAt: new Date(user.updatedAt).toISOString()`。
2. `authenticateUser` 必须先查 `status === "active"` 再验密码，且**无密码用户（passwordHash 为 null）必须直接判失败**——不能把 null 传给 `verifyPasswordHash` 后就当通过。已用测试锁定这两条。

### 安全约定（后续接口必须遵守）

- 密码只以 `scrypt` 哈希 + 随机 salt 落盘（64 字节 hex），**任何返回值都不得带 `passwordHash` / `passwordSalt`**：对外一律走 `toPublicUser()`（测试里显式断言了 `not.toHaveProperty(passwordHash)`）。
- 用户名唯一性判断大小写不敏感（`getUserByUsername` 内部转小写比较）。

### 关键决策（方案没写、必须知道的）

1. **不做索引**（方案原写「+ 索引」）：索引只加速后台列表，认证热路径仍要按记录读 secret；却会引入自己的并发写一致性问题。代价 = 每次读枚举 N 个小文件（N 通常个位数）。
2. **迁移标记 = `applications/migration-state.json`**：每次读本来就要枚举该 namespace → 热路径零额外读。且它会被形态校验过滤掉，不会混进应用列表。
3. **标记只在「确实发现 legacy 文档」时写入**：全新安装不写 → 之后出现的 legacy 文档（备份恢复、回退旧版本后再升级）仍会被导入；迁移过就不再读 legacy → **删掉的应用不会被旧数据复活**（复活 = 已撤销的密钥重新可用，属安全问题）。
4. **legacy 文档保留不删**：回退旧版本时旧代码仍能读到密钥，避免「一降级就全员无鉴权」。
5. **`status: 'disabled'` 立刻生效**：三个鉴权入口 403（OpenAI 风格 / Anthropic `authentication_error`）。虽然本片还没有 API 能设置它，但字段既然存在就必须有效。
6. **错误文案统一到 Application**：`Application name is required` / `Application not found`；存储不可读文案 = `Access key storage is unreadable. Fix the applications storage first.`

### 踩到的坑

- **跑测试期间不要改源码**：vitest 边跑边加载模块，编辑期间启动的那轮结果不可信（本次作废重跑）。
- 目录型 namespace 的文档必须过形态校验，否则按「非法记录」报错（fail closed）；往这些目录手写文档别漏必填字段。
- legacy 一次性导入的测试必须**先写 legacy 文档再读**：若先读过空存储（写标记）再写 legacy，导入不会再发生。

### 设计要点（后续片沿用）

- **余额 = 配额 − 已用量**；已用量按 access key 聚合 usage_events；user 维度 = 该用户名下所有应用的用量之和（按 `ApplicationRecord.ownerUserId` 反查）。
- **UTC 窗口**：日/月边界按 UTC；`total` 永不重置；`resetAt` 由窗口推导，不落库。
- **缓存 10 秒**（配额列表 + 余额），代价是最多 10 秒超发——与方案「须接受少量超发」一致。
- **配额故障 fail open**（异常只打 warn、返回 null），因为配额是资源约束不是鉴权边界；而 `applications` 存储不可读是 fail closed（503）。
- 应用配额优先于归属用户配额；`maxCalls`/`maxTokens` 为 null 表示该维度不限。
- 环境变量：`CODEBUDDY_QUOTA_ENFORCEMENT`（默认 reject，`warn` 只记录）、`CODEBUDDY_USAGE_RETENTION_DAYS`（默认 35）。
- 未做：`/admin-api/quotas` 接口与配额编辑 UI（属 2.6/2.7）；配额开关暂只能改环境变量 + 重启。
