## 现有工作流职责边界（2026-09-16 盘点）

- `ci-main.yml`：push `main` → lint/format:check/typecheck/test:ci（覆盖率门禁）+ Codecov；附带一个**只构建不推送**的 docker-build（tag `codebuddy2api:ci-main`，用于验证 Dockerfile）。
- `ci-pr.yml`：任意 PR → 同四项校验 + `test:patch-branches`（改动分支覆盖率 ≥90%）+ `bun run build`。
- `e2e.yml`：任意 PR + push `main` → Playwright Chromium 跑 `bun run test:e2e`，上传 report artifact。
- `release.yml`：**原有体系里唯一会推送镜像的工作流**；手动 dispatch 生成 `release/vX.Y.Z` PR，该 PR 合并进 main 后才走 verify → 双架构推 `<版本>-<arch>`/`latest-<arch>` → 合并 multi-arch manifest → `gh release create`。
- `docs-pages.yml`：main 上 `docs/**` 变更（或手动）→ VitePress 构建 + GitHub Pages 部署。
- 结论：push 到 `v1` 不会触发任何原有 CI（ci-main/e2e 只认 main，ci-pr 只认 PR），因此手动 `docker-publish.yml` 是 v1 唯一的构建/出镜像入口。

## IDE 提交报 `bun: command not found` 修复（2026-09-16 下午）

- 现象：在 JetBrains IDE 里点提交 → `.husky/pre-commit: line 1: bun: command not found` / `husky - pre-commit script failed (code 127)`，错误里打印的 PATH = `node_modules/.bin:<Xcode git-core>:/usr/bin:/bin:/usr/sbin:/sbin`。
- 根因：**node/npm/bun/bunx 全部装在 `/usr/local/bin`**（node 为官方 pkg 安装；bun 1.4.2 是 `npm i -g bun` 的软链 → `../lib/node_modules/bun/bin/bun.exe`），而 GUI 启动的 IDE 进程 PATH **不含 `/usr/local/bin`**（不读 `/etc/paths`、不跑 shell rc）。终端提交不复现，所以此前一直没暴露。
- 修复（**零仓库改动**，不影响上游 merge）：新建 `~/.config/husky/init.sh`，内容 `export PATH="/usr/local/bin:$HOME/.bun/bin:$PATH"`。husky 的 `.husky/_/h` wrapper 会在每个 hook 执行前 source `${XDG_CONFIG_HOME:-$HOME/.config}/husky/init.sh` —— 这是 husky 官方给 hook 注入环境的入口。
- 验证姿势（复现与回归同一条命令）：`env -i HOME="$HOME" PATH="node_modules/.bin:/Applications/Xcode.app/Contents/Developer/usr/libexec/git-core:/usr/bin:/bin:/usr/sbin:/sbin" sh .husky/_/pre-commit` → 修复前 exit 127，修复后 lint-staged + prettier --check 全过 exit 0。
  - 坑：**不能直接跑 `.husky/pre-commit`**（该文件无 shebang），必须经 `_/pre-commit` wrapper —— husky 用 `sh -e` 执行项目 hook。
- 影响面：pre-commit（lint-staged）、commit-msg（commitlint）、pre-push（lint/format:check/typecheck）三条 hook 全部依赖 bun，一并修好。该文件是**机器级配置**，换机器/重装系统需重建。
