## 限流识别方案（构思，未实施）

- 用户问题：账户被 CodeBuddy 上游限流后不会自动换号，请求持续失败；本轮只要求「先构思如何识别」。
- 排查结论（读代码，未取证报文）：
  1. 选号是 round-robin（`lib/server/domain/credentials.ts:398-413`），候选过滤**只认 token 过期 + access key 范围**（`:368-387`），**完全不存在** cooldown / disabled / 失败计数 / 黑名单。
  2. 上游 `!upstreamResponse.ok` 三处（`lib/server/proxy/codebuddy.ts:2552 / 2638 / 2764`）只透传状态码，**不重试也不换号**；`catch` 统一 500。
  3. 会话亲和（`codebuddy.ts:130-146` + `credentials.ts:747-765`，TTL 24h）会把同一 `x-conversation-id` 继续钉在已限流的凭证上 —— 这是「同一会话反复失败」的根因。
  4. `/v1/responses` 直通上游 body（`codebuddy.ts:2831-2834`），不解析 SSE，**流内错误无法识别**。
  5. usage 埋点只在成功路径写（`codebuddy.ts:156-175`），`logUpstreamFailure`（`:433-464`）不含 credentialFilename → 事后无法统计「某凭证今日失败次数」。
- 方案文档：`.brv/context-tree/projects/codebuddy2api/plans/2026-09-29-rate-limit-detection.md`（brv 提交 `b16d1a2`）。
- 方案要点：限流分 A 额度耗尽 / B 频率限流 / C 凭证失效三类（冷却时长差 2 个数量级）；只在 429 与 401/403 标记（**5xx/网络错误一律不标记**，避免全体凭证被拉黑）；状态放 `manager_state.json.limitedCredentials`；选择算法需**同时**改过滤、兜底回退（全冷却时不返回 null）、游标推进 + 亲和失效三处。
- 待用户拍板 4 项：非流式是否同请求换号重试、是否暴露冷却状态给调用方、多实例是否共享冷却、全局同时受限是否做统一降级。
- 待取证 3 项：真实限流报文（Debug 页 / `.codebuddy_data/debug-logs.json`）、限流窗口粒度（`get-user-resource` 的 `CycleEndTime`）、4 个凭证是否会同时被限。

- **GitHub secrets 仍未生效**：用 `.mcp.json` 的 PAT（用户 `Hucx0211`，仓库 admin=true，接口 200）查仓库级 Actions secrets = **0 条**；仓库 variables 空；org secrets 读不到（403，token 无 `admin:org`）。仓库 `hddara` 是**组织**，故 secrets 很可能被建在组织级但未授予该仓库访问，或建在了 Variables/Environment（workflow 没有 `environment:` 声明读不到 Environment）。
- 两次 `workflow_dispatch`（run `36564127486` / `36584029617`）验证：`Mirror image to Aliyun ACR` 作业成功但步骤 3~6 全 skipped → **「无凭据自动跳过、不阻塞发版」这条降级路径已实测通过**；ACR 推送在 CI 侧仍未验证。
- **本机手动镜像成功（关键验证）**：本机已登录 ACR（`~/.docker/config.json` 的 `auths` 含 `registry.cn-hangzhou.aliyuncs.com`，credsStore=desktop）。ACR 现有 `1.2.2` 与 `latest`，均为 2 平台（linux/amd64 `sha256:332af3c1…` + linux/arm64 `sha256:086db8dc…`，与 ghcr 平台清单 digest **完全一致**）。
- ⚠️ **ACR 拒收 buildx 的 attestation**：buildx 默认给 index 附加 provenance attestation（`unknown/unknown` 平台项，config media type `application/vnd.oci.empty.v1+json`），ACR 个人版 PUT 该子清单报 `403 Forbidden ... unknown manifest class for application/vnd.oci.empty.v1+json`（逐层看：主 index 有 4 项 = amd64 + attestation + arm64 + attestation；`-amd64` 子标签本身也是 index，含 image + attestation）。
  - **解法**：从源 index 里筛出 `platform.architecture ∈ {amd64, arm64}` 的 **digest**，用 `imagetools create -t ACR:tag ghcr@<amd64-digest> ghcr@<arm64-digest>` **重建** ACR 的 index（不复制 attestation）。已固化到两个 workflow 的 ACR 作业里（用 `jq` 过滤）与本地脚本。
- ⚠️ **ghcr.io 直连太慢**：首次从 `ghcr.io` 拉源镜像 10 分钟未完成；改用 `ghcr.nju.edu.cn` 源后 **2.9 秒**完成复制。本地镜像务必用 nju 源（`SOURCE_REGISTRY` 可覆盖）。
