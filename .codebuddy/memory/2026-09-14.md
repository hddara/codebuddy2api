## 存储后端（file / sqlite / pg）事实速查 —— 用户问「file 后端是什么」

`lib/server/storage/index.ts` 一个文件里装了全部三套后端，靠 `getStorageBackendKind()`(:126) 选：

- `CODEBUDDY_STORAGE_BACKEND`（或旧名 `CODEBUDDY_STORAGE_PERSISTENCE`）= file / sqlite / pg
- **兜底返回 `file`**(:150) → 什么都不配的时候就是 file
- 只要设了 `DATABASE_URL` / `CODEBUDDY_STORAGE_PG_URL` 就自动变 `pg`(:146)

### 数据落盘位置

| 后端   | 位置                                                                                               |
| ------ | -------------------------------------------------------------------------------------------------- |
| file   | `CODEBUDDY_STORAGE_FILE_DIR`，默认 `.codebuddy_data`(:89)；旧版 `CODEBUDDY_CONFIG_PATH` 取 dirname |
| sqlite | `CODEBUDDY_STORAGE_SQLITE_PATH`，默认 `<数据目录>/storage.sqlite`(:160)                            |
| pg     | `DATABASE_URL`，schema 固定 `codebuddy2api`(:164)                                                  |

file 后端有**四种文件形态**（全在 `getDocumentPath`:315 里硬编码）：

1. **单文档**：`usage/history`→`usage-history.json`、`debug/logs`→`debug-logs.json`、`debug/settings`→`debug-settings.json`、`admin-auth/state`→`admin-auth.json`、`access-keys/store`→`access-keys.json`
2. **目录型**（一 key 一文件、可枚举，`getNamespaceDirectory`:252）：applications / users / user-sessions / quotas → `<数据目录>/<ns>/<key>.json`
3. **凭据目录**：`credentials/*` → `CODEBUDDY_CREDENTIALS_DIR`，默认 `.codebuddy_creds`
4. **配置单文件**：`config/runtime` → `CODEBUDDY_CONFIG_PATH`

本机实测存在 `.codebuddy_data/usage-history.json`，内容 `{"events": []}`，18 字节，权限 `0600`。

### 四条硬限制（这就是「会话日志/余额仅支持 DB 后端」的真实原因）

| #   | 限制                                                                                                                        | 证据                                                                                                                                                                                                                                                                                        |
| --- | --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **白名单制**：每个 `namespace/key` 必须逐条注册，未注册**直接抛** `Unsupported storage document`                            | `getDocumentPath`:315 / throw :365。DB 后端是通用 `(namespace, document_key)` 表，**零注册**                                                                                                                                                                                                |
| 2   | **不能通用枚举**：`listJson` 只认「目录型 namespace」和 `credentials`，其余抛 `Unsupported list namespace for file backend` | `FileStorageBackend.listJson`:526-537                                                                                                                                                                                                                                                       |
| 3   | **完全不加密**：`FileStorageBackend.putJson`:558 直接 `writeJsonFile`，无任何加密路径                                       | 加密只在 `DatabaseStorageBackend.putJson`:662 且仅限白名单。**且 `encryptPayload`:459 没设 key 时静默降级为 `plain-json`**（不是报错）→ DB 后端不设 key 也是明文落库；只有 `decryptPayload`:483 会在读到密文却无 key 时抛错                                                                 |
| 4   | **没有事件表**：`getEventBackend()`(:903) 对 file **直接抛** `Event storage is only available for database backends`        | ⚠️ 所以 `appendStorageUsageEvents` / `appendStorageDebugLogs` 这些函数在 file 后端**调用即抛**；usage/debug 的 file 分支必须由 **domain 层**用 `getStorageBackendMeta().backend === 'file'` 绕开，走 `usage/history` / `debug/logs` 单文档。**不要在 storage 层直接调 `getEventBackend()`** |

另：`getStorageBackendMeta()`(:968) 返回的 `encryptionEnabled` **只看环境变量有没有设**，与"实际是否真的加密"无关 → 对 file 后端这个字段是误导性的（file 永远不加密，但设了 key 也会显示 true）。

### 为什么 2.5 把 file 后端的用量保留期压到 7 天

file 后端把整段 usage 历史放在**单个** `usage-history.json` 里，`writeJsonFile`(:218) 每次 flush 都 `JSON.stringify` 整个文档重写 → 保留 35 天会让文档体积与写放大 ×5。同理，会话日志（每轮几十 KB、高基数）用 file 后端既不能枚举、又不能建索引分页，故方案决策 6 的"仅 DB 后端"是真实的工程约束，不是随手写的限制。

### 关键设计取舍

1. **不套用 2.x 的 documents namespace**：sessions 是高基数，`documents` 只有 PK `(namespace, document_key)`、无 `(updated_at, session_id)` 索引 → 列表分页会退化成全表扫。
2. **加密必须列级**：`DatabaseStorageBackend.putJson` 的敏感名单在 `putJson` 内部、**只作用于 `documents` 表**，走专用表根本不经过它 → 方案 1.3 原话落不到点上。现在每行带 `encryption_mode`，敏感列存密文或明文 JSON，读侧按行模式解。
3. **file 后端不记录会话日志**（无表可落）：`getSessionBackend()` 用 `instanceof DatabaseStorageBackend` 判定，file 后端一律抛 `Session logging is only available for the sqlite and pg storage backends`；UI 侧用 `getSessionStorageAvailability()` 提示。
4. **`title` 也加密**（它是首条用户消息前 N 字 = 提示词内容），为它给 `sessions` 加了 `encryption_mode` 列（相对方案 1.1 的唯一 DDL 增补）。
5. **计数是读改写**：`appendStorageSessionTurns` = 读旧行 → 合并 `turnCount` / `totalTokens` → upsert；多实例并发写同一会话可能丢一次计数（turns 本身靠主键去重）。已写在代码注释里。
6. **保留清理两个维度**：时间窗口 `trimSessionRecords(before)` + 单会话轮次上限 `trimSessionTurns(sessionId, maxTurns)`（`maxTurns <= 0` = 不限）。

### 与方案 1.2 的三处出入（施工时才发现，已写入施工单）

1. **② 做不到「直接复用反向映射」**：`response-session-index` 存的是 `{bytes, createdAt}` 元数据；`ResponseSession` 自身**不存 `previous_response_id`**（只存 transcript）→ 无法反推链根。必须新增 `conversationRef`。注意它随 session JSON 落盘，**不需要新迁移**。
2. **③ 必须带时间窗口**（方案未写）：`metadata.user_id` 标识**用户**而非会话，不带窗口会把该用户全部会话并成一条 → ③ 与 ④ 共用同一窗口。
3. **③ 仅限 `/v1/messages`**：Chat Completions 也允许 `metadata`，按 `route` 前缀限定，避免误判（有测试覆盖）。

### 设计要点（3.2 接手时会用到）

## 4. Git 无法拉取/推送 诊断（2026-09-14）

用户报「此项目无法拉取代码，也无法推送」。实测定位到**三层原因，互为因果**：

### 实测证据

- `.git/MERGE_HEAD` 存在（41B，mtime Sep 14 18:23），`MERGE_MSG` = `Merge remote-tracking branch 'origin/main'`；`git ls-files -u` 为空 → 冲突早已解决，**只是没收尾 `git commit`**。
- `git pull --dry-run` → `error: You have not concluded your merge (MERGE_HEAD exists). / fatal: Exiting because of unfinished merge.`
- `git push --dry-run` → `.husky/pre-push: line 5: bun: command not found` → `husky - pre-push script failed (code 127)` → `failed to push some refs`。
- `git push --dry-run --no-verify` → `! [rejected] main -> main (non-fast-forward)`。
- 网络/凭据**正常**：`GIT_TERMINAL_PROMPT=0 git ls-remote origin` 成功（远端 main = `f4c6330`），`git fetch --dry-run` = up to date。
- 分叉事实：本地 `700a977 feat(会话日志): 为聊天接口增加会话捕获` ↔ 远端 `f4c6330 feat: add multi-user accounts with quotas, billing and session logs`，各 1 commit。

### 结论

1. **拉取被拒** = MERGE_HEAD 残留：Git 硬规则，只要 `.git/MERGE_HEAD` 存在，`git pull` 一律拒绝，与远端有无新提交无关。
2. **推送被拒（一）** = `.husky/pre-push` 三条 `bun run lint|format:check|typecheck`，本机无 bun（`which bun` 空、`~/.bun/bin/bun` 不存在）→ exit 127 → husky 中止 push。`.husky/pre-commit` 同样是 `bun run lint-staged`，所以 `git commit` 也会被同样拦下。
3. **推送被拒（二）** = 绕过 hook 也推不上，因为 merge 未落地 → 本地不是远端 tip 的快进后继，被 `non-fast-forward` 拒绝。

### 修复路径

收尾 merge（`git commit --no-edit`，让本地包含 `f4c6330`）后 push 即为 fast-forward。bun 缺失需二选一：装 bun（`curl -fsSL https://bun.sh/install | bash`，推荐，因 AGENTS.md 要求 lint/format/typecheck/coverage/build 全绿）或在 PATH 前置 `bun run X` → `npx X` 的 shim；`--no-verify` 会绕过质量门禁，不推荐。

补充：`~/.gitconfig` 的 `url.https://githubfast.com.insteadof=https://github.com` 只改写 HTTPS URL，`origin` 是 SSH（`git@github.com:hddara/codebuddy2api.git`），本次与它无关。

## 5. Git 阻塞问题的修复与推送（2026-09-14）

### 修复动作

1. **装 bun**：`npm i -g bun`（npm prefix = `/usr/local`）→ `/usr/local/bin/bun` 1.4.2。选这个位置是因为它已在 husky hook 打印的 PATH 中；`~/.bun/bin` **不在** hook PATH 里，装那里等于没装。
2. **收尾 merge**：`git commit --no-edit` → `b0fdd47 Merge remote-tracking branch 'origin/main'`。
3. **推送**：`git push` 走 pre-push `bun run lint / format:check / typecheck` 全过 → `f4c6330..b0fdd47 main -> main`；`git ls-remote origin refs/heads/main` 与本地 HEAD 均 `b0fdd47`，状态 `## main...origin/main`（无 ahead/behind）。

### 中途发现的第四个坑：系统里藏着一个 Git 2.15.0

第一次 `git commit` 失败，报的不是 bun 而是：

```
Error: ✖ lint-staged requires at least Git version 2.32.0.
[cause]: 'git version 2.15.0\nsizeof-long: 8'
```

- 来源：`/usr/local/bin/git -> ../git/bin/git`，即用户早年装的 Git for Mac（`/usr/local/git/bin/git`），版本 **2.15.0**（`sizeof-long: 8` 是老版 `git version` 的独有输出）。
- 为什么会被选中：我的 shell 里 `which -a git` 首个是 Xcode 的 2.50.1，但 **lint-staged 通过 execa 起子进程时，PATH 被 npm-run-path 类机制把 `/usr/local/bin` 提前**，于是命中 2.15.0。同类风险：GUI 启动的 IDE 走 `/etc/paths`（首行就是 `/usr/local/bin`），`git` 也会是 2.15.0。
- 修法：`ln -sfn /opt/homebrew/bin/git /usr/local/bin/git`（2.15.0 → 2.49.0），**可逆**：还原写 `ln -sfn ../git/bin/git /usr/local/bin/git`。`/usr/local/git/` 本体未删。改完 lint-staged 正常通过。

### 复查方式（下次排查用）

- `git --no-pager status --branch` + `ls .git/ | grep -E 'MERGE|rebase|lock'`：判断是否被半途 merge/rebase 卡住。
- `git pull --dry-run` / `git push --dry-run`：直接拿到真实报错，比读代码推断快。
- `git push --dry-run --no-verify`：判断 hook 故障与远端拒绝（non-fast-forward）各占几成。
- hook 里报 `command not found` 时，husky 会把完整 PATH 打出来，直接比对哪个目录先命中。
- 枚举 PATH 中所有 git 及版本：`echo $PATH | tr ':' '\n' | while read d; do [ -x "$d/git" ] && echo "$d/git -> $("$d/git" --version | head -1)"; done`。
