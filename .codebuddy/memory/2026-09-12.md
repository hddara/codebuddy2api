### 关键决策（方案未写、需要知道的）

1. **写权限一律 owner**：`GET /admin-api/users*`、`/admin-api/quotas*` 放开给 owner+admin（读），创建/更新/删除用户、设置/删除配额只给 owner。要给 admin 写权限只需换常量。
2. **内置 owner 的账号密码不在用户路由里改**：`admin-auth` 里还存了一份 owner 密码，改用户记录会让 legacy 兜底登录继续接受**旧密码**（`resolveLoginUser` 用 `username === state.username` + `state.password` 校验）。保护方式：PATCH 命中「user 记录 == 当前 `state.username` 对应用户」且带 `password`/`username` 时返回 409，引导走密码设置或 `/me/password`。
3. **末位 owner 保护**：降级/禁用/删除最后一个 active owner 一律 409 `last_owner`；删除自己 409 `cannot_delete_self`（先于 last_owner 判断）。
4. **`/me` 不接受 role/status**：member 只能改 displayName 与 preferences（`normalizeUserPreferences` 白名单：`sessionLogEnabled` / `usageRange` / `timeZone`）。
5. **业务逻辑放在 `lib/server/**`**：`app/**` 被 coverage exclude，所以校验/枚举/余额聚合等可测逻辑都下沉到 domain 层，路由只做参数解析与状态码映射。
6. **错误形状统一**：新路由一律 `{error:{code,message}}`，码为 `invalid_json` / `invalid_request` / `not_found` / `conflict` / `last_owner` / `cannot_delete_self` / `console_owner_credentials` / `invalid_credentials`，401/403/503 复用 session/rbac 既有码。
7. **配额 owner 必须存在**：`quotaOwnerExists` 拒绝给不存在的 app/user 建配额（防手滑写出永不生效的文档）。

### 浏览器实测发现并修复的缺陷（已改代码）

`app/users/users-controller.tsx` 的 `onSubmit` **总是把 `username` 一起提交**（表单里预填了用户名），导致编辑内置 owner 时命中 `console_owner_credentials` 守卫：①只改角色/显示名也会被拒；②提示文不对题（显示的是「密码与用户名请在设置处修改」而不是 `last_owner`）；③**内置 owner 的显示名在 UI 上根本改不了**。修法：仅当输入的用户名与当前记录不同才发送 `username`。修复后重测：降级 → `last_owner` 文案正确；显示名可改（`PATCH /me`/users 均 200）。

## 计费模型诊断（用户报告「用户计费模式存在错误」后的只读调查结论，未改代码）

**后端事实（已确证，附行号）**：

- 额度只存 `quotas` namespace：`{ownerType:'app'|'user', ownerId, period:'daily'|'monthly'|'total', maxCalls, maxTokens}`，key = `${ownerType}-${period}-${ownerId}`，**maxCalls/maxTokens 为 null = 不限**（`lib/server/domain/quotas.ts:16-21,166-176`）。
- `app` owner = **一个 API Key**（applications namespace 里的记录，即管理台「凭证管理」里的 API Key，含 `secret`（明文）、`credentialFilenames`、`ownerUserId`）；`user` owner = 用户。
- 请求判定 `getAccessKeyQuotaViolation`（`domain/quotas.ts:487-517`）：**先查 key 级 → 再查 user 级，任一超限即拦**（key 违规短路，不查 user）；`DEFAULT_QUOTA_PERIOD='monthly'` 写死；无 quota 记录或两维均 null → 放行；`ownerUserId` 为空则**只查 key、完全不查用户余额**（`:502`）。返回 429（OpenAI 形状 `insufficient_quota`，Anthropic 形状 `rate_limit_error`），可用 env `CODEBUDDY_QUOTA_ENFORCEMENT=warn` 降级为只告警（`lib/server/proxy/auth.ts:18-62,169`）。
- 已用量**实时聚合 `usage_events`**（非计数器）：`getBalance` → `resolveOwnerAccessKeyIds` → `getUsageTotalsForAccessKeys`（`domain/quotas.ts:322-359`、`domain/usage.ts:890-936`）。user 级的 used = 该用户名下**所有** key 的用量加总（`resolveOwnerAccessKeyIds` 用 `ownerUserId` 过滤 applications，`domain/quotas.ts:303-316`）。
- `usage_events` 落 `access_key_id`/`access_key_name`/`credential_filename`/token 明细，所以 key 维度与 user 维度都能算。
- member 经 `POST /me/applications` 建 key 时 `ownerUserId` 恒为当前登录用户（`app/me/applications/route.ts:78`）；domain 层兜底 `?? null`（`domain/applications.ts:429`）。

**结论**：后端「key 有额度则按 key 限、key 不限仍扣用户余额」的双层语义**本身是对的**。真正缺的是产品入口：①「凭证管理」的 API Key 卡片/表单**没有任何 Token 额度字段**，分配额度只能去「配额」页选 owner=应用；②用户余额账户没有独立呈现（用户管理页无余额列、建/改用户不能设余额）；③管理端直建且未传 owner 的 key 会绕过用户余额（`domain/quotas.ts:502`）。

## 改造方案（用户两条需求的合并设计）：用户余额账户 + 每 Key 额度 + 用户级账户/模型分配

**目标模型**：

```
用户 (users namespace, UserRecord.preferences)
├─ Token 余额账户     quota(ownerType='user', period='monthly', maxTokens)          [已有后端，缺管理入口]
├─ 可用上游账户(路由账户) UserPreferences.allowedCredentialFilenames: string[]|null  [新增，缺省/null=全部]
└─ 可用模型            UserPreferences.allowedModels: string[]|null                 [新增，缺省/null=全部]
    └─ API Key (applications, ownerUserId)
```

4. **凭证集合（新增）**：实际可用上游凭证 = `key.credentialFilenames ∩ user.allowedCredentialFilenames`，空集 → 403
5. `/v1/models`：只返回该用户可用模型（受 allowedModels 约束）
